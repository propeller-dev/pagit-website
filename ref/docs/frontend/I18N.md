# Internationalization (i18n)

Pagit uses a simple client-side internationalization system for the Next.js frontend, supporting English (EN) and Portuguese (PT).

## Current Architecture (V2 Key Structure)

The i18n dictionaries were reorganized to support large UX refactors and reduce key sprawl.

The root namespaces are now:

- `ui`: Shared UI primitives and reusable copy (actions, labels, feedback, table UI, dialogs, theme selector, navigation labels)
- `lookups`: Runtime/code-driven labels (status, intervals, payment methods, notification event types/statuses/channels, etc.)
- `features`: Feature/page/component copy (dashboard, billing, integrations, charges, customers, users, profile, auth, onboarding, etc.)
- `public`: Public-facing flows (checkout/receipt pages outside the authenticated dashboard)
- `routes`: Route title/breadcrumb copy used as the single source for metadata + breadcrumbs

Examples:

- `ui.actions.cancel`
- `ui.table.pagination.nextPage`
- `lookups.notification.eventType.ChargeReminder`
- `features.integrations.whatsapp.title`
- `public.receipts.uploading`
- `routes.pages.pendingReviews.title`
- `routes.labels.edit`

## Implementation Details

The system is built on two core components:

1.  **`I18nProvider`**: A React context provider that wraps the application and manages the current locale state.
2.  **`useTranslation` Hook**: A hook that provides the `t()` function for translating strings and the `setLocale()` function for switching languages.

The root layout and `I18nProvider` also keep the `<html lang>` attribute synchronized with the active locale (`en` or `pt-BR`) and mark the app as `notranslate`. Shared portal-heavy UI primitives (`Select`, dialogs, dropdowns, tooltips, popovers, command palette, etc.) are also marked `translate="no"` for the same reason. This is intentional because the product already owns EN/PT translation and browser auto-translation can mutate portal-based UI (Radix/dialog/select/tour layers), causing unstable DOM errors during navigation and interactions.

### Dictionaries

Dictionaries are kept in `src/i18n/dictionaries/` as TypeScript files (`en.ts`, `pt.ts`). This provides better type safety and autocompletion than JSON files.

```typescript
export const en = {
  ui: {
    actions: {
      cancel: 'Cancel',
      save: 'Save Changes',
    },
  },
  features: {
    profile: {
      title: 'Profile',
    },
  },
};
```

Both dictionaries must remain in **EN/PT key parity** (same paths, different values).

### Dictionary Typing

- `TranslationKey` is generated from the dictionary schema (`src/i18n/types.ts`)
- The schema is derived from `en.ts` but widened to `string` values so `pt.ts` can type-check safely
- This keeps strong key typing without forcing locale values to match literal English strings

## Usage

### In Client Components

Use the `useTranslation` hook to access localized strings:

```tsx
'use client';

import { useTranslation } from '@/i18n/I18nContext';

export function MyComponent() {
  const { t } = useTranslation();
  
  return (
    <h1>{t('ui.navigation.labels.dashboard')}</h1>
  );
}
```

### Parameterized Strings

The `t()` function supports simple parameter replacement:

```typescript
// In dictionary
subscribedTo: 'Subscribed to {name}'

// In component
t('features.onboarding.subscribedTo', { name: 'Premium Plan' })
```

The `t()` resolver supports repeated placeholders (all `{name}` occurrences are replaced).

## Route Copy (Metadata + Breadcrumbs)

Route copy is centralized under `routes.*` and used as a single source of truth for:

- page metadata titles (`generateTranslatedMetadata`)
- breadcrumb labels (`useBreadcrumbs`)

Helpers:

- `getRoutePageCopy(dict, routeKey, 'title' | 'breadcrumb')`
- `getRouteLabel(dict, 'new' | 'edit' | 'detail')`

This avoids duplicated `metadata.*` and `breadcrumbs.*` dictionaries.

## Dynamic Lookups (Avoid string-concatenated `t()` keys)

For runtime values (statuses, intervals, event types, channels, etc.), use lookup helpers from `src/i18n/lookups.ts` instead of building template-string keys manually:

- `tLookupInterval(...)`
- `tLookupChargeType(...)`
- `tLookupChargePaymentMethod(...)`
- `tLookupNotificationEventType(...)`
- `tLookupNotificationChannel(...)`
- `tLookupNotificationStatus(...)`
- `tLookupNotificationFailReason(...)`

This removes most `t(\`...\` as any)` usage and centralizes normalization logic (for example `credit_card -> creditCard`).

## Language Switcher

A language switcher is integrated into the `UserNav` component in the dashboard sidebar. Users can toggle between 🇺🇸 English and 🇧🇷 Português. The selection is persisted in `localStorage`.

## Data Tables and Column Labels

Data tables use a translation pattern for column headers. There are two ways columns can be labeled:

### Method 1: Simple Translation Keys (Recommended)

Define columns with translation key strings as headers:

```typescript
// columns.tsx
export const userColumns: ColumnDef<User>[] = [
  {
    accessorKey: 'email',
    header: 'ui.labels.email'  // Translation key
  },
  {
    accessorKey: 'role',
    header: 'ui.labels.role'
  }
];
```

The table component automatically translates these keys:

```typescript
// Table component
const translatedColumns = useMemo(() => {
  return columns.map((col) => ({
    ...col,
    header: typeof col.header === 'string' && col.header.includes('.')
      ? t(col.header as any) // dynamic column keys still use a guarded cast
      : col.header
  })) as ColumnDef<TData, TValue>[];
}, [columns, t]);
```

### Method 2: Using meta.label (For Advanced Cases)

For more complex scenarios, you can provide a `meta.label`:

```typescript
{
  id: 'name',
  accessorKey: 'name',
  header: ({ column }) => (
    <DataTableColumnHeader column={column} title={t('ui.labels.name')} />
  ),
  meta: {
    label: t('ui.labels.name'), // Used by View dropdown
  }
}
```

### View Dropdown

The "View" dropdown in data tables (`DataTableViewOptions`) displays column names. It automatically:

1. First checks for `meta.label`
2. Then checks if `header` is a translation key (contains `.`)
3. Falls back to capitalizing the column ID

This ensures column names are properly translated in the View dropdown.

## Best Practices

1. **Always use translation keys**: Never hardcode user-facing text
2. **Use the correct root namespace by intent**:
   - shared UI primitives -> `ui.*`
   - runtime/code labels -> `lookups.*`
   - feature/page/component copy -> `features.*`
   - route metadata/breadcrumb labels -> `routes.*`
   - public flows -> `public.*`
3. **Prefer explicit UI slots in feature keys**: group by page/component area (`page`, `cards`, `dialogs`, `toasts`, `forms`, `tables`, `states`, etc.) when adding new copy
4. **Avoid new flat key blobs**: especially under large domains like `features.integrations.*`
5. **Avoid dynamic template-string translation keys**: use lookup helpers for code-driven values
6. **Keep EN/PT in sync**: every key added to `en.ts` must be added to `pt.ts` in the same task
